Agreed decisions. The project follows the course structure exactly: app.js, server.js, middleware/logger.js, routes/, controllers/, data/store.js, validators/, the browser client in public/ and tests in tests/. Data lives in an in-memory store with seed data (no database). There are no models/, no db/, no separate error-handler file and no staff login. Customers book and order through the chat, by phone (+34 627 41 09 35) or by email (owners@paalhu.es); the chat can only do what the endpoints can do. Validators only say what is wrong and in which field; the controllers and the error handler choose the HTTP status code.

Move the error handler from src/middleware/errorHandler.js to the end of app.js (after the 404) and delete the file. Delete the empty src/models/. Everything else in step 1 is done.
Step 2 · Browser client in public/

Step 3 · Data store (src/data/store.js)
One module that owns all the data, so controllers never touch files.
  • Seed data: dishes and drinks from reference.md with an id, name, category, price in cents and spice level.
  • Orders: an in-memory array with an id counter. Create, list, get one, change status. The total is calculated here from dish prices.
  • Bookings and waiting list: the store creates one booking engine (abrirLibro()) and exports it. The chat, the new controllers and the staff CLI all use the same rules.
  • Exports a reset() so each test starts from the seed data.
Step 4 · Validators per resource
Split validators.js into src/validators/ as in section 3. Update the imports in chatController.js. The chat also starts checking time, notes and reference. Every new controller validates its body, params and query before calling the store.

5. Details to take into account

Server and Express

PointDetail
Order inside app.jslogger → express.json() → express.static('public') → routers → 404 → error handler. The error handler goes last and has 4 arguments (err, req, res, next).
Express 5 and asyncErrors thrown in async handlers reach the error handler on their own: no try/catch in every route.
Madrid timeprocess.env.TZ = 'Europe/Madrid' stays the first line of server.js. Tests must set it too (Jest setupFiles), or dates shift.
Keep the chat workingpublic/app.js relies on GET /api/chat/status returning { enabled } and on the 503 while the chat is off. Same URLs, same answers.
Private filesOnly public/ is served. src/, .claude/ (customer data), node_modules/, package*.json and .env are never reachable.
Jest with ES modulesThe project uses "type": "module". Run Jest as node --experimental-vm-modules node_modules/jest/bin/jest.js in the "test" script.
Tests and real dataThe booking engine writes to reservas.json. In tests, set RESERVAS_DATOS to a temporary file so tests never touch real bookings.

Errors and status codes

PointDetail
Who decides the codeValidators throw ValidationError (message + field); the store throws its own errors with a status. Only the error handler turns them into 400 / 404 / 409 / 500.
Error answer formatAlways { error, field? }. On 500, never send internal details (stack, file paths); log them on the server.
Success codes200 for reads and changes, 201 for a POST that creates something.
Don't leak data"Not found" must be the same whether the booking doesn't exist or the phone doesn't match (the chat already does this).

Data and privacy

PointDetail
In-memory storeOrders are lost when the server restarts; that is accepted for the course. Bookings keep their JSON file because the engine already saves them.
Customer data off GitHubreservas.json and *historial.jsonl stay in .gitignore.
What customers seeNever table numbers, nor other customers' names or phones.
Nothing is deletedCancelling = PATCH status: "cancelled". Every booking change is written to the history.
Channelchat, phone or email (today chat / equipo). Requests send phone or email; only the server sets chat.
Order totalCalculated in the store from the seed prices; never trust a total or price sent by the client. Work in cents.
Spanish field namesThe booking engine uses fecha, hora, personas, nombre, telefono, notas, estado. The API uses English; the controller maps them, as runTool in chatController.js does today.
