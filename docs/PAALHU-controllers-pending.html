2. How every controller function works

Each function follows the same four steps:

  1. Read the request: req.query (after the ?), req.params (the :id) or req.body (the JSON sent).
  2. Validate it with the rules of the worksheet. A wrong value throws a ValidationError (src/validators.js), which errorHandler.js turns into 400 { error, field }.
  3. Use the data: find, filter, save or change it.
  4. Answer with res.json(...) and the right status: 200, 201 created, 401 not logged in, 404 not found, 409 conflict.

3. What each remaining function must do

Menu screen

2 · GET /api/dishes → getDishes
Reads?category=&search=&allergen=&spice=&sort=&page=&limit=
DoesKeeps dishes of that category id, whose name contains search, that do not contain allergen, with spice ≤ spice. Sorts (- = descending; default: category, then name) and returns one page.
Rulespage from 1 (default 1) · limit 1–100 (default 20) · spice 0–3 · allergen from a fixed list · sort only on known fields. Anything else → 400.
Answers200 { data, page, limit, total, totalPages }
NeedsThe dish data: id, category id, name, price, spice 0–3, allergens. Prices from pages/menu.html. The page() and limit() validators already exist.
3 · GET /api/drinks → getDrinks
Reads?search=&sort=&page=&limit=
DoesSame as dishes, with only search, sort (default: by name) and paging.
Answers200 { data, page, limit, total, totalPages }
NeedsThe 5 drinks with prices from the menu. Reuses the sorting and paging written for dishes.
4 · GET /api/menus → getMenus
ReadsNothing. Short, fixed list, no paging.
Answers200 with the menus: À la carte and Set menu (€12.90, Monday to Friday, lunch only).
5 · GET /api/menus/:id → getMenu
Reads:id in the URL.
DoesReturns one menu with its contents, for the set menu pop-up: its four courses (starter, main, dessert or coffee, drink) and their options from pages/set-menu.html.
Answers200 the menu · 400 id not a whole number · 404 no menu with that id.

Login screen

6 · POST /api/clients → signUp
ReadsBody { name, email, phone, password }
Rulesname 2–50 characters · valid email, not already registered · phone 9–15 digits, optional + · password at least 8 characters.
DoesSaves the client with the password hashed (never in plain text).
Answers201 the client without the password · 400 invalid field · 409 email already registered.
NeedsA clients list, and password hashing (Node's built-in crypto, no extra package).
7 · POST /api/auth/login → login
ReadsBody { email, password }
Rulesvalid email · password not empty and matching the stored one.
Answers200 { token, client } · 400 invalid field · 401 wrong email or password (same message for both).
NeedsA way to give and check tokens, and a small login check run before functions 9 and 10: it reads Authorization: Bearer <token> and answers 401 if it is missing or wrong.

Booking screen

These three use the booking engine that already exists (.claude/skills/paalhu-reservas/reservas-core.mjs): tables, shifts, joining tables and free-table checks. It is the same register the chat and the staff use, so a table booked on the website is taken for everyone.

8 · GET /api/reservations/availability → getAvailability
Reads?date=&guests=, both required.
DoesLists the arrival times of that day that still have a free table for that many guests.
Answers200 the free times (empty when closed) · 400 missing or invalid date or guests (1–10).
9 · POST /api/reservations → createReservation (login)
ReadsBody { date, time, guests }. Name and phone come from the logged-in client.
Rulesdate YYYY-MM-DD, today or later, not a closed day · time HH:MM and one of that day's times · guests 1–10 and a table must be free.
Answers201 the reservation · 400 invalid field or closed day · 401 not logged in · 409 no free table at that time.
NeedsThe engine must remember which client made the reservation, so function 10 can check it.
10 · PATCH /api/reservations/:id → changeReservationTime (login)
Reads:id (like R-20261114-001) and body { time }.
DoesMoves the client's own reservation to another time on the same day.
Answers200 the changed reservation · 400 invalid time · 401 not logged in · 404 not found or not this client's · 409 cancelled, or no free table at the new time.
